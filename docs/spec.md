#  Scripts Manager — спецификация

Локальное WPF-приложение для запуска параметризованных скриптов (T-SQL, PL/pgSQL, PowerShell, Python).
Замена Red Gate SQL Scripts Manager, скрипты для которого лежат в
[perspect/filer/db-scripts](https://myserver/perspect/filer/db-scripts).

## Что не устраивает в Red Gate (и что должно быть здесь)

| Red Gate | Здесь |
|---|---|
| Нет даты/даты-времени — даты вводятся текстом и парсятся `try_convert` | Типы `date`, `datetime` с пикером |
| Нет необязательных параметров — «пустое» значение `-` | `required: false`, пустое значение передаётся как `NULL` |
| Видит только свою папку без подпапок, репозиторий надо разворачивать в `C:\ProgramData\Red Gate\...` | Несколько корней скриптов в любых папках, подпапки — категории |
| PowerShell заявлен, но не работает | PowerShell — полноценный runner |
| Python — IronPython с объектом `RedGate` | Обычный CPython; параметры и подключения — аргументы и переменные окружения |
| Только MS SQL | MS SQL и PostgreSQL, несколько подключений на скрипт |
| Скрипт и разметка формы — один XML с CDATA | Скрипт — обычный `.sql`/`.ps1`/`.py`, манифест `.yaml` — в `.manifests` |

## Скрипты и их источники

- **Корень скриптов** — папка со скриптами. Корней несколько, задаются в настройках:
  - командный — клон git-репозитория (новый, отдельно от db-scripts — в db-scripts не пишем);
  - личный — локальная папка или свой репозиторий.
- В дереве слева: корень → подпапки → скрипты. Дополнительно фильтр по тегам и поиск по названию.
- **Скрипт** = файл `.sql`/`.ps1`/`.py` в папке скриптов + манифест и пресеты в служебных папках корня:

  ```
  <корень>/Работа с очередями/Explore Queue Data.sql                 — скрипт
  <корень>/.manifests/Работа с очередями/Explore Queue Data.sql.yaml — манифест (параметры, подключения)
  <корень>/.presets/Работа с очередями/Explore Queue Data.sql.yaml   — пресеты
  <корень>/.output/Работа с очередями/Deploy/                       — вывод скрипта Deploy.ps1 (OUTPUT_DIR)
  ```

  В имени манифеста и пресетов — расширение скрипта, поэтому `Имя.ps1` и `Имя.py` не конфликтуют. Папки скриптов
  остаются чистыми, а всё служебное лежит в одном месте. Папки, начинающиеся с точки, в дерево не попадают.
  Манифест, у которого нет файла скрипта (скрипт удалён или переименован), показывается в дереве с ошибкой.
  Файл скрипта можно открыть во внешнем редакторе (кнопка) и посмотреть во встроенном просмотрщике с подсветкой.

### Git

Работа через `git.exe` (учётные данные и настройки разработчика):
- индикатор «есть изменения на сервере» (`git fetch` при старте и по кнопке), «Обновить» — `git pull --ff-only`; после него (и после F5) карточка выбранного скрипта перечитывается, а если его манифест изменился — введённые значения сбрасываются к новым значениям по умолчанию;
- отметка локально изменённых и новых скриптов (`git status`);
- «Опубликовать» — commit выбранного с сообщением и `git push` в текущую ветку. В окне публикации скрипт — одна строка (файл скрипта и манифест публикуются вместе), под ней — изменённые пресеты по одному (новый, изменён, удалён); пресеты по умолчанию не отмечены. Если отмечена часть пресетов файла, в коммит попадает опубликованная версия файла с отмеченными изменениями, остальные остаются неопубликованными в рабочей папке. Коммит собирается во временном индексе git, уже подготовленное в основном индексе (`git add`) не затрагивается;
- «Копировать в…» — копирование скрипта (скрипт, манифест, пресеты) из одного корня в другой (личный → командный).
- «Удалить…» (меню скрипта в дереве, кнопка в карточке) — файл скрипта, манифест и пресеты в корзину Windows, после подтверждения со списком файлов; опустевшие папки в `.manifests` и `.presets` убираются, папка вывода `.output` с логами остаётся. Выполняющийся скрипт не удаляется. Если корень под git, удаление публикуется через «Опубликовать…», как любое изменение.

Конфликты и ветки — вне UI, в обычном git.

## Манифест

`.manifests/Работа с очередями/Explore Queue Data.sql.yaml`:

```yaml
title: Сообщения в очередях
description: Просмотр данных, находящихся в очереди, с декодированием тела из base64
runner: tsql              # tsql | plpgsql | powershell | python — должен подходить к расширению файла скрипта
tags: [Работа с очередями]
output: [grid, log]       # grid — таблицы результатов, log — сообщения; по умолчанию оба
confirm: false            # true — подтверждение перед запуском (для изменяющих скриптов)
rerun: false              # true — кнопка «Запустить ещё раз» на вкладке «Результат»

connections:
  - name: connection      # имя в скрипте
    type: mssql           # mssql | postgres
    scope: database       # database (сервер + БД) | server (только сервер)
    default: { server: myserver, database: mydatabase }

params:
  - name: fdate
    label: Дата с
    type: datetime
    required: false
    help: Пусто — сутки назад. Время попадания в очередь (UTC)
  - name: tdate
    label: Дата по
    type: datetime
    required: false
  - name: ttop
    label: First N
    type: int
    default: 100
    min: 0
  - name: queue
    label: Очередь
    type: list
    editable: true        # можно ввести своё значение
    items: [DelayedMessageQueue, ProcessingMessageQueue, HeavyMessageProcessingQueue, HeavyMessageProcessingDelayedQueue]
    default: DelayedMessageQueue
  - name: recipient
    label: To App
    type: string
    required: false
```

## Пресеты

Пресет — сохранённый набор значений формы: параметры и подключения. Все пресеты скрипта лежат в одном файле
`.presets/<путь скрипта>.yaml` (YAML-список). Пресеты, закоммиченные в git, видны всем; пока пресет не опубликован,
он есть только в рабочей папке пользователя.

`.presets/Работа с очередями/Explore Queue Data.sql.yaml`:

```yaml
- name: Роуминг                      # обязательно, показывается в списке пресетов
  values:                            # необязательно: параметр → значение (строкой, как в форме)
    queue: DelayedMessageQueue
    ttop: 500
    fdate: today-7                   # для дат — выражения, как в default
    stands: [dev, stage, prod]        # несколько значений — для list с multi: true
    recipient: []                    # пустой список — очистить поле
    query: |-                        # многострочное значение — блоком
      select top (10) *
      from t
  connections:                       # необязательно: подключение → сервер и база
    connection: { server: myserver, database: mydatabase }
- name: Неделя
  values: { fdate: today-7 }
```

- `server` — как в поле сервера на форме: хост, алиас SQL Client или `хост,порт`; порт можно указать отдельно (`port: 5433`). `database` не нужна для `scope: server`.
- При выборе пресета сначала подставляются значения по умолчанию, затем значения пресета. Параметры, которых нет в пресете, остаются по умолчанию.
- Неизвестные параметры и подключения, неподходящие значения — замечания в карточке скрипта, запуску не мешают: такие значения просто не подставляются.
- «Сохранить как…» на форме записывает текущие значения в файл пресетов (с тем же именем — заменяет), «Удалить» — удаляет пресет из файла; последний пресет удаляется вместе с файлом. Перед записью файл перечитывается, чтобы не потерять пресеты, появившиеся в нём после открытия формы (например, после `git pull`).
- Публикация — через «Опубликовать», по одному пресету (см. «Git»).

### Типы параметров

| Тип | Контрол | Значение в SQL | Значение в PS/Python |
|---|---|---|---|
| `string` | строка | `nvarchar(max)` | строка |
| `text` | многострочное поле (`multiline` по умолчанию) | `nvarchar(max)` | строка |
| `int` | число (`min`, `max`) | `bigint` | строка числа |
| `decimal` | число | `decimal(38, 10)` | строка с точкой |
| `bool` | флажок | `bit` / `boolean` | `true` / `false` |
| `date` | пикер даты | `date` | `yyyy-MM-dd` |
| `datetime` | пикер даты + время | `datetime2` / `timestamp` | `yyyy-MM-ddTHH:mm:ss` |
| `guid` | строка с проверкой формата | `uniqueidentifier` / `uuid` | строка |
| `list` | выпадающий список; `multi: true` — выпадающий список с флажками (выбранные — через запятую в поле; поиск, если элементов больше 8); `editable: true` — со своим значением | одиночный — значение (`key`, если есть); множественный — JSON-массив строкой (`OPENJSON` / `json_array_elements_text`) | одиночный — значение; множественный — JSON-массив |
| `folder` | выбор папки | `nvarchar(max)` | путь |
| `file` | выбор файла (`filter`) | `nvarchar(max)` | путь |
| `range` | многострочное поле: числа и диапазоны `a..b` через запятую или с новой строки (`19..28, 41..43, 1`), порядок сохраняется, `b < a` — по убыванию; под полем — количество номеров и повторы; `min`, `max` — для каждого номера; не больше 10 000 номеров | JSON-массив чисел строкой | массив чисел (PS — `-имя @(19, 20)`, для `[int[]]`) |

Элементы `list`: `[a, b]` или `[{ key: 1, value: Тест }, ...]` — показывается `value`, передаётся `key`.

Общие атрибуты: `name` (обязательно), `label`, `help`, `required` (по умолчанию `true`), `default`.
`default` для дат допускает выражения `now`, `today`, `today-7`, `now-1h`.
Незаполненный необязательный параметр передаётся как `NULL` / пустое значение.

## Подключения

- Окно подключения как в SSMS:
  - **MS SQL**: сервер (хост или алиас SQL Client, `хост,порт`), аутентификация Windows / SQL (логин, пароль), БД — выпадающий список с сервера (для `scope: database`);
  - **PostgreSQL**: хост, порт (5432), БД (список с сервера), логин, пароль или «из pgpass».
- Строку подключения вводить не нужно.
- **Недавние подключения** запоминаются (`%APPDATA%\ScriptsManager\connections.json`), пароли — в Windows Credential Manager. Выбор сервера — поле с выпадающим списком недавних.
- На форме скрипта у каждого слота из `connections` своё поле выбора. Последний выбор запоминается для скрипта.
- В заголовке результата видно, на каком сервере/БД был запуск.

## Запуск

### T-SQL
- Скрипт выполняется как пакет `SqlCommand` с параметрами `@<name>` — объявлять их в скрипте не нужно (как в Red Gate).
- Чтобы скрипт запускался и вне приложения (SSMS), параметры можно объявить в блоке между строками `--#region Params` и `--#endregion`. При запуске из приложения строки блока очищаются (номера строк в ошибках не сдвигаются). Окно правки пересобирает блок при сохранении. Объявления действуют только до первого `GO`.
- Разделитель `GO` поддерживается: пакеты выполняются по очереди на одном подключении, параметры передаются в каждый.
- Подключение — слот с именем из манифеста. Если слотов несколько, скрипт выполняется на первом; остальные доступны только как параметры `@<слот>_server`, `@<слот>_database` (например, для linked server).
- `PRINT`, `RAISERROR` с severity ≤ 10 — в лог в момент получения; каждый результирующий набор — отдельная вкладка-таблица.

### PL/pgSQL
- Скрипт выполняется на первом подключении (PostgreSQL) целиком; операторы делит Npgsql (с учётом `$$`-блоков).
- Обычные запросы — параметры `@<name>` (Npgsql подставляет только те, что встречаются в тексте). Множественный `list` — JSON-строка (`json_array_elements_text(@name::json)`).
- В `DO $$ ... $$` параметры передать нельзя, поэтому перед выполнением runner вызывает `set_config('param.<name>', <значение>, false)` для каждого параметра (имя в нижнем регистре, незаданное значение — пустая строка), а скрипт читает `current_setting('param.<name>', true)`.
- `RAISE NOTICE` — в лог, результаты — таблицы.
- Ошибка — код SQLSTATE, текст, подробности, подсказка и контекст PL/pgSQL. Номер строки в файле Npgsql не сообщает, поэтому показывается позиция от начала оператора.

### PowerShell
- По умолчанию Windows PowerShell 5.1 (`powershell.exe`), в настройках можно выбрать `pwsh`.
- **Файлы `.ps1` — в UTF-8 с BOM**: без BOM Windows PowerShell читает их в ANSI и портит кириллицу.
- Скрипт вызывается из временной обёртки (`-File`) с именованными аргументами для блока `param()`: `bool` — `-имя:$true/$false` (подходит и для `[switch]`, и для `[bool]`), множественный `list` и `range` — массив, незаданный параметр не передаётся (срабатывает значение по умолчанию из `param()`). Код возврата — `exit N` скрипта, при необработанной ошибке — 1.
- Подключения — переменные окружения для каждого слота (`<SLOT>` — имя слота в верхнем регистре):
  - `DB_<SLOT>_CONNSTR` — для MS SQL строка, которую понимают и System.Data.SqlClient (Windows PowerShell), и Microsoft.Data.SqlClient; для PG — строка Npgsql;
  - `DB_<SLOT>_SERVER`, `DB_<SLOT>_PORT`, `DB_<SLOT>_DATABASE`, `DB_<SLOT>_USER`, `DB_<SLOT>_PASSWORD`, `DB_<SLOT>_INTEGRATED`.
- `SCRIPT_PARAMS` — все параметры одной JSON-строкой.
- `OUTPUT_DIR` — постоянная папка вывода скрипта `<корень>/.output/<путь скрипта без расширения>` (создаётся при запуске): логи и другие файлы, которые нужно сохранить. Неотслеживаемые файлы из `.output` в git-статусе приложения не показываются и не публикуются. В карточке PowerShell- и Python-скрипта — вкладка «Вывод»: файлы папки (новые сверху, с датой и размером) и содержимое выбранного (UTF-8 или Windows-1251; от файла больше 4 МБ — конец); «Обновить», «Открыть папку», «Открыть файл» (и двойной щелчок), «Удалить». Список перечитывается при открытии вкладки и после завершения запуска.
- `RESULT_DIR` — временная папка запуска; файлы `*.csv` (разделитель `;`, `,` или табуляция) и `*.json` (массив объектов) из неё после завершения показываются вкладками-таблицами.
- stdout — в лог, stderr — в лог как ошибки; ненулевой код возврата — ошибка запуска.

### Python
- Интерпретатор — путь в настройках (по умолчанию `python` из PATH). PATH читается из реестра при каждом запуске, поэтому изменения PATH подхватываются без перезапуска приложения; заглушка `python.exe` из WindowsApps (открывает Microsoft Store) пропускается.
- Параметры — `--<name> <значение>` (список — `--<name> a b`, для argparse `nargs="*"`; `bool` — флаг `--<name>`, только если «да», как `action="store_true"`; незаданный не передаётся) и `SCRIPT_PARAMS`; подключения — те же переменные окружения, дополнительно `DB_<SLOT>_ODBC` (строка для pyodbc, «ODBC Driver 17 for SQL Server») и для первого подключения PG — `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`.
- Вывод, `RESULT_DIR` и `OUTPUT_DIR` — как у PowerShell. Запуск с `-u` (небуферизованный вывод), `PYTHONUTF8=1`.

### Общее
- Перед запуском — проверка обязательных параметров и форматов; `confirm: true` — диалог с сервером/БД и значениями.
- Кнопка «Остановить»: `SqlCommand.Cancel` / `NpgsqlCommand.Cancel`, для процессов — завершение дерева процессов.
- Время выполнения и число строк в каждой таблице.
- Таблицы: щелчок по заголовку строки или столбца выделяет его (Ctrl — добавить, Shift — диапазон); правый щелчок по заголовку столбца — сортировка, если строк не больше 5000; даты в ячейках — `yyyy-MM-dd HH:mm:ss`, числа от пяти цифр — с пробелами между разрядами (только при показе, копирование и выгрузка берут исходные значения); Ctrl+C — выделенное, Ctrl+Shift+C — с заголовками (TSV, вставляется в Excel); сохранение в xlsx (без сторонних библиотек) или CSV; «Копировать как ▾» (кнопка и контекстное меню): выделенное, а если выделено не больше ячейки — вся таблица, в разметке Jira / Confluence, Markdown или как `select * from (values …) as t (…)` для SQL Server / PostgreSQL; там же «Показать текстом…» — окно с текстом; бинарные поля — hex с ограничением длины.
- Несколько запусков одновременно, в том числе одного и того же скрипта (например, на разных серверах): «Запустить» не блокируется, пока скрипт выполняется. На вкладке «Результат» — выбор запуска этого скрипта (время, подключение, состояние), если их несколько.
- `rerun: true` (в окне правки — «Повторный запуск»; по умолчанию и у манифестов без поля — выключено): на вкладке «Результат» кнопка-значок «Запустить ещё раз» — новый запуск с параметрами и подключениями выбранного запуска (значения, уже разобранные при первом запуске, в том числе относительные даты, и тот же пароль); прежний результат остаётся. Недоступна, пока выбранный запуск выполняется; `confirm: true` спрашивает подтверждение и здесь.
- Под деревом — список «Запуски» за сеанс (новые сверху), граница между ним и деревом перетаскивается: значок состояния (разной формы: стрелки — выполняется, галочка — выполнено, крестик — ошибка, квадрат — остановлено), название, время начала, подключение, длительность; в заголовке — сколько выполняется. Щелчок открывает скрипт на вкладке «Результат» с этим запуском (поиск и теги сбрасываются, если скрипт скрыт). Меню запуска: «Открыть результат», «Переименовать…» (своё название вместо названия скрипта — например, сервер; пусто — вернуть), «Удалить результат» (выполняющийся — только после остановки); те же кнопки — на вкладке «Результат». «Убрать завершённые» — убрать все завершённые вместе с результатами.
- Оповещение о завершении: у скрипта в дереве значок — стрелки, пока выполняется, и значок итога, пока результат не посмотрели (открыть вкладку «Результат» с этим запуском при активном окне); такие запуски в списке — жирным. Если результат не на экране — сообщение в правом нижнем углу окна с кнопкой «Открыть» (скрывается через 15 с или когда результат посмотрели). В строке состояния — итог и длительность. Если окно неактивно — ещё мигает кнопка на панели задач и всплывает уведомление Windows; щелчок по нему открывает результат.

## Добавление и правка скриптов

Файлы `.sql`, `.ps1`, `.py` без манифеста в `.manifests` показываются в дереве серым курсивом. Запустить их нельзя; «Изменить…» открывает окно правки с этим файлом, и при сохранении создаётся манифест. Файл скрипта перезаписывается, только если изменился текст (например, добавился блок `--#region Params`).

Окно «Добавить скрипт…» (кнопка, меню папки, файл перетащен в главное окно) и «Изменить…» (меню скрипта, кнопка в карточке):
- скрипт — из файла (`.sql`, `.ps1`, `.py`; UTF-8 или Windows-1251) или вставкой текста; язык — по расширению или по тексту (для `.sql` — T-SQL или PL/pgSQL);
- теги — плашками: выбор из тегов других скриптов или новый (Enter), × — убрать;
- название, описание, теги, подтверждение перед запуском, вид вывода; для нового — папка со скриптами, подпапка и имя файла;
- параметры находятся в тексте: T-SQL — `DECLARE` в начале скрипта (тип и значение по умолчанию, `getdate()`/`dateadd` → `now`/`today±N`); PL/pgSQL — переменные `DECLARE` первого блока `DO` (имя параметра — как у переменной, например `l_from`, тип и значение по умолчанию из объявления, `current_date`/`now()` и сдвиги `- 1`, `- interval '2 hours'` → `today-1d`/`now-2h`; записи и курсоры пропускаются), а также `@имя` и `current_setting('param.имя')`; PowerShell — `param()` (разбор AST через powershell.exe: тип, `Mandatory`, `HelpMessage`, `ValidateSet`, значение по умолчанию; `[int[]]` без `ValidateSet` — `range`, `(19..28) + (41..43)` → `19..28, 41..43`); Python — `add_argument` (type, default, required, help, choices, nargs, store_true). Без типа — строка, если значение по умолчанию не подсказывает другой;
- у каждого найденного параметра — отметка «сделать параметром»: снятая — переменная остаётся в скрипте. В T-SQL при сохранении объявления всех параметров, а также `@<слот>_server` и `@<слот>_database` дополнительных подключений, собираются в блок `--#region Params` (на прежнем месте, новый — в начале скрипта); `DECLARE` отмеченных переменных из начала скрипта переносятся в него, остальные не трогаются. Тип и выражение из скрипта сохраняются, если тип не изменился и выражение даёт то же значение по умолчанию; иначе они строятся по параметру (`today-7` → `dateadd(day, -7, cast(getdate() as date))`). Переменные из блока при правке сразу отмечены как параметры;
- PowerShell и Python получают значения аргументами, поэтому при сохранении параметры манифеста, которых нет в скрипте (например, добавленные вручную), объявляются в нём; существующие объявления не меняются. PowerShell — в конец блока `param()` (по AST; блока нет — новый перед первым кодом, после `using`): тип по параметру (`[string]`, `[long]`, `[decimal]`, `[bool]`, `[datetime]`, `[guid]`, `[string[]]`, `[int[]]` для `range`), значение по умолчанию, если это литерал (`today-7` вычисляет приложение), подсказка — комментарием. Python — `add_argument` перед `parse_args()` своего парсера скрипта; парсера нет — блок `#region Params` … `#endregion` после заголовка (`#!`, комментарии, docstring) с парсером и переменными `имя = _args.имя` (ключевые слова — `from_`); блок пересобирается при следующих сохранениях. PL/pgSQL: в блок `DO` значения передать нельзя, поэтому переменная с именем параметра в `DECLARE` первого блока `DO` получает значение `nullif(coalesce(current_setting('param.имя', true), <прежнее значение>), '')::<тип>` — вне приложения настройки нет и действует прежнее значение (литерал или выражение `(…)::text`), пустое значение из приложения — NULL; объявления в начале строки получают отступ 4 пробела; недостающие параметры дописываются в конец `DECLARE` (без `DECLARE` — новым перед `BEGIN`) как `имя <тип>`, значение по умолчанию — литералом, `today-1d` — `(current_date - interval '1 day')::text`. Уже связанные объявления (кроме отступа), параметры, которые скрипт берёт сам (`@имя`, `current_setting('param.имя')`), и скрипты без `DO` не меняются;
- у параметра можно изменить имя, приглашение, подсказку, тип (в том числе путь к папке или файлу), обязательность, значение по умолчанию, диапазон, элементы списка, фильтр файлов; параметры можно добавлять, удалять и переставлять;
- подключения: имя, СУБД, «только сервер»; для PowerShell и Python находятся по `DB_<ИМЯ>_*`;
- при правке YAML перезаписывается целиком (комментарии в нём теряются); пресеты следуют за переименованием параметров и подключений (значения удалённых параметров из них убираются).

## Фильтр по тегам

Над деревом — плашки всех тегов. Отмеченные сужают список: остаются скрипты, у которых есть все отмеченные теги (И); работает вместе с поиском. Кнопка × снимает все.

## Перенос скриптов из Red Gate

Скрипты из db-scripts перенесены один раз (в папку `samples`, позже удалена из репозитория), импорта `.rgtool` в программе нет.

| Скрипт | Перенос |
|---|---|
| Active queries, Root blocks | как есть, `scope: server` |
| Empty Delayed Queue | как есть, `confirm: true` |
| Explore Queue Data, Resend Delayed Messages | `fdate`/`tdate` → `datetime`, необязательные; `recipient`/`ToApp`/`id` → необязательные (`id` — `guid`); обработка `-` убрана; Resend — `confirm: true` |
| Decode Kafka Message | Python без `RedGate`: `--query` |
| Export Binary Data | переписан на PowerShell (System.Data.SqlClient); параметры `Connection`, `folder`, `query` — как в Red Gate, пресеты подходят |

## Архитектура

- .NET 10, WPF, MVVM (CommunityToolkit.Mvvm).
- Проекты:
  - `ScriptsManager.Core` — модель манифеста и загрузка (YamlDotNet), валидация, подключения, runners, git;
  - `ScriptsManager.App` — WPF: дерево скриптов, форма параметров (DataTemplate на тип), окно подключения, результаты;
  - `ScriptsManager.Tests` — тесты загрузки манифестов, подстановки параметров, runners.
- Пакеты: Microsoft.Data.SqlClient, Npgsql, YamlDotNet, AvalonEdit (просмотр скрипта).
- Настройки — `%APPDATA%\ScriptsManager\settings.json` (корни скриптов, пути к интерпретаторам), секреты — Credential Manager.
